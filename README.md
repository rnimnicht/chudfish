# chudfish

Naive betting market arbitrage strategy

Polymarket had just introduced 15-min Crypto markets, and the liquidity was very low, so there was a small window of free arb. We were seeing ~15/hr in test trades for about a month before the window closed.

Deployed to EC2 via Github Actions with MongoDB backing database.

## Architecture Overview

 - **Listeners** - pull live websocket data from Kalshi/Polymarket APIs into Redis
 - **Trader** - Trade strategies are supported as a constant loop. This is to support trade confirmation and to avoid issues with stale data.
 - **Metric Client** - Ingests the Trader's publish execution information from a Redis Pub/Sub. The betting market APIs neccessitate an extra REST call to get fill information, so this design offloads that extra latency.
 - **Client** - HTML+CSS autogenerated by Claude. It's a mess. I'm not good at frontend :P

## Stack

Python FastAPI w/ Pydantic, uvloop for fast async, MongoDB because NoSQL allowed very quick iteration. Docker Compose, Github Actions deploying to an EC2 medium(?) instance.

## Cool things that are supported

 - Multiple toggle-able trading strategies
 - Multiple toggle-able market streams, supporting different types of markets (e.x. 1hr-crypto, 15min-crypto, long-standing event markets)
 - Infra for expanding into other orderbook websockets (e.x. using backing binance streams for more complicated strategies)

## The strategy we used (written [somewhat poorly tbh] in /trader/strategies/crypto_15_min_arb_strategy)

1. Ensure orderbook freshness (orderbook timestamp < 500ms old and != last orderbook timestamp)
2. Check arb sum is < 0.xx (<0.99 means free $$ so we should execute a trade - though we set it to ~0.97 to diffuse losses from trade execution failures)
3. Check that the arb percentage is above a minimum danger 0.xx (backing data is slightly different [rolling window vs. point price] - this is our catch strategy for market divergence)
4. Check there's enough tradeable volume on both sides (minimum $1 bet for both sites)
5. Now we want to capture all the tradeable volume in the orderbook that satisfies a successful arb
6. If the total tradeable volume > minimum required liquidity, execute the trade (we would tweak this parameter depending on how many trade failures we were seeing)
7. Execute trade, publish metrics, continue to next trade :D
